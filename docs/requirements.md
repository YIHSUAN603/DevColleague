# DevColleague 需求規格

> 狀態：草案
> 最後更新：2026-11-10

## 1. 產品定位

DevColleague 是一套**給開發者個人使用的桌面 AI 助理**，目標是像一位同事一樣陪伴日常開發工作：
彙整散落在各平台的工作資訊、協助處理重複性的流程，並在需要時主動提醒。

### 1.1 基本決策

| 項目 | 決定 |
|---|---|
| 使用形式 | 桌面應用程式（Tauri） |
| 目標使用者 | 個人使用（單一使用者、資料存在本機） |
| AI 角色 | 以 LLM 為核心 |
| 運作方式 | LLM 驅動：助理自己在對的時間把事情做完再告知，而不是等使用者按按鈕。由程式決定何時喚醒 LLM，由 LLM 決定要做什麼、是否需要通知 |
| 優先整合平台 | ADS/TFS（Azure DevOps Server）、GitHub |

### 1.2 不在範圍內（目前）

- 多使用者、帳號系統、權限管理
- 雲端同步、多台裝置共用資料
- 計費與多租戶
- 即時協作功能

## 2. 使用情境

1. **早上開工**：打開 DevColleague，一眼看到待審查的 PR、被指派的 Work Item、昨晚失敗的建置。
2. **站會前**：一鍵產生「昨天做了什麼、今天要做什麼」的摘要。
3. **送 PR 前**：選擇分支，自動產生 PR 描述，並先做一輪 AI Code Review。
4. **建置失敗時**：AI 自動讀取 Pipeline log，指出可能原因和修正方向。
5. **隨時提問**：在對話視窗中詢問「我有哪些 PR 擱超過三天？」等問題，AI 自己去查詢並回答。
6. **一句話派工**：對管家說「下週要交報告」，管家把工作拆給不同角色（例如查行程、整理相關 Work Item、找出舊筆記），彙整後一次回覆。
7. **晨間流程**：每天早上開機後，助理自動產生上一個工作日的日報告草稿、整理今天的待辦並跳出通知，點開即可接著追問。
8. **寫日報告**：下班前或隔天早上，選擇日期、補上會議等事項，產生當天的日報告，逐一貼到團隊文件中各專案底下。

## 3. 功能需求

### 第一階段：MVP「我的工作台」（已實作）

#### F1. 平台連線管理
- 設定 ADS/TFS 與 GitHub 連線（伺服器網址、Personal Access Token）
- 支援多個連線（例如同時連 ADS 與 TFS 兩台伺服器）
- 測試連線、顯示連線狀態
- Token 必須安全儲存（使用作業系統的憑證儲存區，不以明文存放）

#### F2. 統一儀表板
- 跨平台彙整顯示：
  - 我建立的 PR
  - 待我審查的 PR
  - 指派給我的 Work Item／Issue
  - 最近的建置／Pipeline 結果
- 可依平台、專案、Repo 篩選
- 點擊項目可開啟原平台頁面

#### F3. AI 對話助理
- 以自然語言提問，AI 透過工具（tool use）查詢平台資料後回答
- 回覆以串流方式即時顯示
- 保留對話紀錄，可切換、刪除對話
- 可在對話中切換 LLM Provider 與模型

#### F4. 工作摘要
- 依時間區間（今日、昨日、本週、自訂）彙整 commit、PR、Work Item 活動
- 產生站會報告或週報
- 可複製為 Markdown

#### F5. LLM Provider 設定
- 支援 API 模式，可切換多家（至少 Claude，其他如 OpenAI、本機模型）
- 支援 CLI 模式，第一版支援 Claude Code（`claude -p`）與 Codex CLI（`codex exec`）
- 設定預設 Provider 與模型
- 詳見 [架構設計：LLM Gateway](architecture.md#4-llm-gateway)

### 追加功能（已實作）

#### F15. 日報告
- 產生可貼到團隊日報告文件（Google 文件，每天一張表、依專案與成員分區）的個人內容
- 專案對應設定：依文件中的順序列出日報告專案，各自對應一個平台專案（ADS 專案或 GitHub repo）；
  對應不到的活動歸在「未分類」
- 依報告日期彙整當天的 commit、PR、Work Item 異動，並依日報告專案分組
- 工作項目的進度百分比由 Work Item 父子階層計算（已完成的子項目數 ÷ 子項目總數）；
  沒有對應 Work Item 的工作項目沿用前一份日報告的數字並標示「待確認」
- 可手動補充會議、包版、待確認問題等平台上看不到的內容，一併交由 LLM 整理
- 每天的內容存在本機，下次產生時帶入最近一份，讓工作項目名稱與進度能接續
- 產生後可編輯；依專案逐一複製，貼到文件時保留巢狀清單與連結
- 報告日期預設為當天；早上 10 點前（日報告的繳交期限）預設為上一個工作日
- 不自動寫回 Google 文件、不讀取本機 Repo（未 push 的 commit 不會出現）
- 日報告分為「草稿」與「定稿」（配合 F14 實作）：例行流程自動產生的內容一律為草稿，
  不會覆蓋使用者編輯過或已定稿的內容；使用者補充、確認後才成為定稿

### 第二階段：LLM 驅動的助理

這個階段把 DevColleague 從「使用者按按鈕才執行」改為「助理自己在對的時間把事情做完再告知」。
喚醒 LLM 的來源有三種：時間到（F14 排程）、平台有變化（F9）、使用者在對話中交代（F14）。
喚醒之後要查什麼、做什麼、是否值得通知，由 LLM 透過工具自行決定。

以下依實作順序排列。

#### F16. 背景常駐與通知（已實作）
- 開機後自動啟動並常駐系統匣，不顯示主視窗；可在設定中關閉開機啟動
- 關閉視窗時縮到系統匣，背景繼續執行；從系統匣選「結束」才完全停止
- 以系統通知告知結果，點擊通知開啟對應的對話或頁面

#### F14. 例行流程（Routine）
- 使用者可定義例行流程，例如晨間流程、站會報告、週報
- 每個 Routine 包含：提示範本、觸發方式、通知方式；F13 完成後可再指定執行角色
- 觸發方式：排程（cron 格式）、手動（按鈕或對話中輸入指令，例如 `/morning`）
- 可在對話中以自然語言建立、修改、停用 Routine（例如「以後每天早上幫我整理日報告」），
  由 LLM 透過工具設定；因為會改變之後的自動行為，套用前在對話中請使用者確認
- 執行結果存成一段對話，系統通知點開後可直接接續追問
- App 未執行期間錯過的排程，可設定在下次啟動時補跑一次
- 無人值守執行時可使用的工具：唯讀查詢、本機寫入（日報告草稿、記憶）與通知；
  會修改外部狀態的工具預設不允許，需在 Routine 中明確允許
- 每次執行送給 LLM 的資料與工具呼叫過程存入執行紀錄，可事後查看
- 無人值守執行使用 Routine 指定的 Provider，未指定時使用預設 Provider；F17 完成前僅支援 API 模式
- 內建「晨間流程」範本：產生上一個工作日的日報告草稿，並整理今天的待辦
  （待審查的 PR、指派的 Work Item、失敗的建置、前一份日報告中進行中的項目）後通知
- F4 的站會報告與週報作為內建 Routine 範本提供
- 詳見 [架構設計：例行流程](architecture.md#8-例行流程routine)

#### F9. 事件提醒
- 背景定期檢查平台（預設每 5 分鐘，可在設定中調整），由程式比對與上次檢查的差異：
  - 被提及（@）或被指派審查
  - 建置失敗
  - PR 擱置超過指定天數
- 有變化時才喚醒 LLM，由 LLM 參考記憶判斷是否值得通知、如何摘要；沒有變化時不呼叫 LLM
- 每日喚醒次數設有上限，避免 token 花費失控
- 透過系統通知顯示

#### F10. 個人知識庫與記憶
- 記錄設計決策、踩坑筆記
- 記住使用者的偏好、目前正在處理的工作項目與進度
- 助理可在對話或例行流程中透過工具自行記下這些內容；使用者可查看、修改、刪除
- 對話與例行流程執行時自動引用相關記憶
- 第一版使用全文搜尋（SQLite FTS5），資料量變大後再評估加入向量搜尋

#### F17. 內建工具的 MCP 轉接（CLI 模式）
- 後端把內建工具（平台查詢、日報告、記憶、通知、Routine 管理）以 MCP Server 的形式提供給 CLI Provider，
  讓 Claude Code、Codex CLI 也能執行例行流程與事件提醒
- 只監聽 `127.0.0.1` 並驗證 token
- CLI 仍維持不得修改檔案、不得執行指令的限制，只額外開放這組工具
- 詳見 [架構設計：MCP 整合](architecture.md#6-mcp-整合)

### 第三階段：開發流程輔助

#### F6. PR 助理
- 選擇本機 Repo 與分支，產生 PR 標題與描述
- 摘要他人的 PR 變更內容
- 建立 PR 到 ADS 或 GitHub

#### F7. AI Code Review
- 針對 PR diff 給出初步審查意見
- 可載入自訂審查規範（例如團隊的 .NET／Vue 規範）
- 審查意見可選擇是否回寫為 PR 留言

#### F8. 建置失敗診斷
- 讀取失敗的 Pipeline log
- 指出可能原因、相關程式碼位置與修正建議

#### F11. 本機 Repo 理解
- 對本機專案進行程式碼問答
- 變更影響分析
- 適合交由 CLI Provider（例如 `claude -p`）處理

### 第四階段：「AI 秘書團隊」

#### F12. MCP 工具擴充
- 後端作為 MCP Client，可接入任意 MCP Server（stdio 與 Streamable HTTP），
  讓 Email、行事曆、筆記軟體等外部系統不必自行撰寫 integration 即可成為 LLM 工具
- 設定格式相容常見的 `mcpServers` 寫法（`command`、`args`、`env`），方便從其他工具複製設定
- MCP Server 需要的 Token 存放於作業系統憑證儲存區，不以明文寫入設定
- 設定畫面顯示每個 MCP Server 的連線狀態與提供的工具清單，可個別啟用／停用工具
- 會產生副作用的工具（例如寄信、建立事件）預設需經使用者確認才執行
- API 模式與 CLI 模式都能使用同一份 MCP 設定
- 詳見 [架構設計：MCP 整合](architecture.md#6-mcp-整合)

#### F13. 角色（Role）與管家派工
- 使用者可定義多個角色，每個角色包含：名稱、職責說明、人設與語氣、可使用的工具、偏好的 Provider／模型
- 角色以 Markdown 檔定義，可直接編輯，也可在設定畫面管理；提供數個內建範本
- 「管家」為特殊角色：只負責判斷要派給哪些角色、彙整結果，不直接呼叫業務工具
- 一次對話可同時派工給多個角色並行處理
- 角色定義按需載入，管家平時只看到各角色的簡短說明，避免佔用 context
- 對話中可直接指定與某個角色對話，略過管家
- UI 顯示派工過程（例如「已交給 PR 秘書處理…」）
- F14 的 Routine 可指定執行角色，預設為管家
- 詳見 [架構設計：角色與派工](architecture.md#7-角色與派工)

### 待決事項

- 產品定位是否擴及開發以外的個人事務（例如 Email、行事曆、帳單）：F12 的架構不限制可接入的系統，
  但內建角色與 Routine 範本要涵蓋到哪些範圍，待決定後再更新本文件。

## 4. 非功能需求

| 類別 | 需求 |
|---|---|
| 安全性 | Token 與 API Key 使用作業系統憑證儲存區；後端只監聽 `127.0.0.1`；送給 LLM 的資料需讓使用者知情（手動執行時事前顯示；無人值守執行時存入執行紀錄供事後查看） |
| 隱私 | 所有資料預設存在本機，不上傳到 DevColleague 自己的伺服器（沒有這種伺服器） |
| 效能 | 儀表板首次載入在 3 秒內顯示快取資料，再於背景更新 |
| 平台 | 優先支援 Windows，架構上保留 macOS／Linux 的可能性 |
| 可擴充性 | 新增平台整合或 LLM Provider 時，不需要修改上層功能程式碼 |
| 語系 | 介面以繁體中文為主 |

## 5. 決策紀錄

| 日期 | 事項 | 決定 | 理由 |
|---|---|---|---|
| 2026-11-04 | 多家 API 的串接方式 | 自行為每家撰寫 adapter，不使用 LiteLLM | 能完整運用各家特有功能（例如 Claude 的 prompt caching），減少大型相依套件 |
| 2026-11-04 | 後端打包工具 | PyInstaller | 最普及、設定簡單、文件多 |
| 2026-11-04 | 第一版支援的 CLI 工具 | Claude Code（`claude -p`）、Codex CLI（`codex exec`） | 兩者都支援非互動模式與結構化串流輸出 |
| 2026-11-04 | 主動提醒的背景執行方式 | 縮到系統匣繼續執行，預設每 5 分鐘檢查 | 關閉視窗後仍能收到提醒，又不會開機就佔用資源 |
| 2026-11-04 | 知識庫搜尋方式 | 先用 SQLite FTS5 全文搜尋 | 不需要 embedding 模型，個人資料量初期不大 |
| 2026-11-09 | 外部系統的擴充方式 | 後端實作 MCP Client，非核心平台透過 MCP Server 接入；ADS/TFS、GitHub 仍維持自寫 integration | 現成 MCP Server 生態豐富，不必每家各寫 integration；核心平台需要統一資料模型與儀表板，仍自行實作 |
| 2026-11-09 | 角色的定義方式 | 以 Markdown 檔（YAML frontmatter + 內文 prompt）定義 | 好編輯、可版控，格式接近 Claude Code subagent，CLI 模式容易轉換 |
| 2026-11-09 | 管家派工的層數 | 只允許一層：管家派給角色，角色不能再派工；角色之間的轉交一律經過管家 | 避免無限遞迴與 token 失控，流程容易追蹤 |
| 2026-11-09 | Routine 的排程方式 | 與 F9 主動提醒共用同一個背景排程器 | 同樣依賴系統匣常駐，避免重複實作 |
| 2026-11-09 | 本機模型的串接方式 | 以 OpenAI Chat Completions 相容 adapter 同時支援 OpenAI 與 Ollama 等本機模型 | 主流本機模型服務都提供相容端點，一個 adapter 即可涵蓋 |
| 2026-11-09 | CLI 模式的權限 | 非互動執行時只開放唯讀能力（Claude Code 限 Read／Grep／Glob；Codex 使用 read-only sandbox） | 無人可即時確認，避免 CLI 自行修改檔案或執行指令 |
| 2026-11-09 | session token 傳遞方式 | 以環境變數傳給後端，不放在命令列 | 命令列參數可被本機其他行程讀取 |
| 2026-11-09 | 工作摘要的資料揭露 | 產生報告前先在 UI 顯示彙整後、將送給 LLM 的資料 | 符合「送給 LLM 的資料需讓使用者知情」 |
| 2026-11-10 | 日報告的輸出方式 | 在 App 內產生、編輯後依專案複製貼上，不自動寫回 Google 文件 | 文件由多人共用，寫錯位置會影響他人；也不需要另外處理 Google 授權 |
| 2026-11-10 | 日報告的資料來源 | 只取 ADS/TFS、GitHub 上的 commit、PR、Work Item，不讀取本機 Repo | 當天的工作大多會 push，沿用既有的平台整合即可 |
| 2026-11-10 | 日報告專案與平台專案的對應 | 一個日報告專案對應一個平台專案，於設定畫面選擇 | 實際使用上大致一對一，設定最簡單 |
| 2026-11-10 | 日報告的進度百分比 | 由 Work Item 父子階層計算並以其為準；沒有對應 Work Item 時沿用前一份日報告的數字並標示待確認 | 進度是給 PL 掌握狀況的資訊，不應由 LLM 推測 |
| 2026-11-10 | 產品的運作方式 | 改為 LLM 驅動，採混合式：程式決定何時喚醒 LLM（排程、平台變化、對話交代），LLM 決定做什麼、是否通知 | 原本每項功能都要使用者按按鈕才執行，不符合「同事」的定位；若每次輪詢都喚醒 LLM 則花費高、行為難預測 |
| 2026-11-10 | 階段順序 | F9、F10、F14 提前為第二階段，並新增 F16（背景常駐與通知）、F17（內建工具的 MCP 轉接）；開發流程輔助順延為第三階段 | 配合 LLM 驅動的方向，先完成讓助理能自己做事的基礎 |
| 2026-11-10 | 背景執行方式 | 開機啟動並常駐系統匣，可在設定中關閉（取代 2026-11-04「不開機啟動」的考量） | 晨間流程要在使用者不動手的情況下執行 |
| 2026-11-10 | 無人值守執行的 LLM 模式 | API 模式與 CLI 模式都支援；先完成 API 模式，CLI 模式透過 F17 取得內建工具 | CLI 模式可使用訂閱方案；但 CLI 無法直接呼叫 DevColleague 定義的工具，需另外轉接 |
| 2026-11-10 | 無人值守執行的資料揭露 | 啟用例行流程或事件提醒即視為同意；每次送給 LLM 的資料存入執行紀錄，可事後查看 | 無人值守時沒有人能事前確認；事前確認會讓早上仍需要動手一次 |
